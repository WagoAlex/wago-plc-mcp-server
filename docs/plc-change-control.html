Change control for a PLC fleet

Änderungssteuerung für eine Steuerungsflotte

How a configuration change, a reboot, and a firmware update reach a controller once GitOps mode is switched on. Written for engineers who use GitHub as a code repository and have not run a build pipeline before.

Wie eine Parameteränderung, ein Neustart und ein Firmware-Update auf eine Steuerung gelangen, sobald der GitOps-Betrieb aktiviert ist. Für Fachkräfte, die GitHub als Quellcode-Ablage kennen, aber bislang keine Build-Pipeline betrieben haben.

Three classes of change, and who may make each

Every action against a controller falls into exactly one of these classes. The class decides who is allowed to perform it, and that decision is enforced in code on the server, not by convention.

Read

Assistant, directly

Values, diagnostics, status. Nothing on the device changes.

  • Firmware version and build across the fleet
  • Update status and progress during a flash
  • Any of the roughly 400 device parameters

Configure

Proposed, then reviewed

Writable settings. In GitOps mode the assistant cannot write to the device; it produces a change file for the configuration repository instead.

  • NTP servers, SNMP, hostname
  • Serial interface assignment
  • 0-0-docker-enabled

Consequential

Named person required

Reboot, factory reset, firmware. In GitOps mode the assistant can only propose one. In live mode the call is denied unless that exact method ID has been put on the allowlist, and the denial is logged either way.

  • Reboot and restart
  • Firmware update and downgrade
  • Factory reset, formatting

The four participants

Each has one job. Nothing in this system lets one of them take over another's.

The assistant

Reads the fleet and drafts change files. Talks to the controllers through the MCP server over the WAGO device REST interface.

Writes nothing to a device in GitOps mode. Never flashes firmware unless that exact method ID sits on the allowlist.

You, the engineer

Review a proposed change, add your name to it, and merge it. This is the only point in the chain where a human decision is recorded.

Merging is the approval. Nothing runs before it.

The configuration repository

A normal Git repository holding one file per device plus the firmware policy. It is the record of what the fleet is supposed to look like.

The file is the instruction. An uncommitted edit authorizes nothing.

The job runner

A small service on a PC inside the plant network. It watches the repository, and when an approved change lands it carries that change out against the devices.

It must sit inside the plant network. A cloud machine has no route to the controllers.

Procedure 1: switch a setting, using Docker as the example

Applies to any writable parameter. Docker is shown because it is a setting with real consequences for what the controller runs.

Enable the container runtime on 192.168.42.119

0-0-docker-enabled  false → true
  1. Engineer

    State the intent in plain language

    "Enable Docker on the PFC300 at 192.168.42.119." The assistant first reads the current value, so the change is made against the device as it is, not as it was assumed to be.

  2. Assistant

    A change file is produced instead of a write

    With GitOps mode on, the write is intercepted. What comes back is a file for the device, listing the parameter and its intended value.

    # plcs/192.168.42.119.yaml
plc_ip: 192.168.42.119
managed_parameters:
  0-0-docker-enabled: true
  3. Engineer

    Open a change request and read the difference

    On GitHub this is a pull request. It shows the old value beside the new one, the same way a diff shows a changed line of code. Nothing has reached the controller at this point.

  4. Runner

    A rehearsal runs automatically on the change request

    The runner reads the live values from the controller and prints the difference it would apply. It does not write. This is the step that catches a device that is unreachable, or a value that someone already changed by hand.

    [192.168.42.119] Drift detected (1 parameter):
  0-0-docker-enabled: False → True
Dry-run. Pass --execute to apply.
  5. Engineer

    Approve and merge

    Your approval on the pull request is the authorization. It is recorded against your GitHub account, not typed into the file.

  6. Runner

    The change is written, and only the difference

    The same comparison runs again, this time writing. A parameter already at the intended value is left alone, so re-running is harmless. The audit log records which parameters changed; who approved the change stays with the pull request.

Procedure 2: reboot a controller

A reboot is not a setting: it happens once and cannot be undone by editing a file afterwards. It therefore uses a one-shot instruction that is deleted after it runs.

Restart the Edge Controller at 192.168.42.121

ops/reboot-edge-121.yaml  0-0-device-reboot
  1. Assistant

    The reboot is refused, and a proposal is written

    Asked to reboot the device, the server refuses the call and returns a one-shot file. The field approved_by is deliberately empty.

    plc_ip: 192.168.42.121
action: invoke_method
method_id: 0-0-device-reboot
requires_human: CRITICAL
approved_by: ""
  2. Engineer

    Open the change request; it is safe to leave open

    An unapproved proposal cannot execute. You can raise it now and merge it during the next maintenance window without any risk in between.

  3. Engineer

    Approve during the window, then merge

    Merging is what starts the job. Plan it the way you would plan walking to the cabinet and power-cycling the device, because the effect is the same.

  4. Runner

    The method is called once, then the file is removed

    The instruction is deleted from the repository after it succeeds, so it cannot be replayed by accident on the next run. A failure leaves it in place for a retry.

Procedure 3: firmware update, and downgrade

Firmware is the one change a later commit cannot reverse. It uses the same one-shot instruction as a reboot, plus two checks that exist only here.

Update the Edge Controller at 192.168.42.121 to build 31

ops/fw-edge-121.yaml  target 4.9.1
  1. Engineer

    Check the revision is permitted for this device

    The firmware policy lists, per controller, which revisions it may run. The default installed when no revision is named is the newest permitted one.

    # firmware-policy.yaml
192.168.42.121: { allowed: ["4.9.1"] }
  2. Engineer

    Raise the instruction and approve it

    Same shape as a reboot: one device, one revision, an empty approved_by until you merge.

  3. Runner

    The correct image is selected from the hardware, not the filename

    The controller is asked for its own order number and firmware build. Each available image is opened and matched against that order number. Where two images match, the job stops and lists them rather than guessing.

    Device identity: order=0752-8303/8000-0002  firmware=04.09.01(31)
Resolved: TP-Linux_update_V040901_31 (build 31)
  4. Runner

    Two preconditions are checked before anything is written

    The controller must already be at or above the minimum build for its type, and the installed version must fall inside the range the image itself declares acceptable. Both are refusals, not warnings.

  5. Runner

    Transfer, install, restart

    The image is transferred in segments, the controller installs it and restarts itself. It is unreachable for part of this. Progress stops at roughly 93 percent and never reaches 100: completion is signalled by the status, not the percentage.

    fwstatus: Started (3)  progress: 61%
[device unreachable - restarting]
fwstatus: Unconfirmed (4)  progress: 93%
Done. fwstatus: Inactive (0)  firmware version: 04.09.01

Downgrading to an earlier release

A downgrade is the same procedure with an older revision named. It is not a special mode and needs no separate tooling. Two conditions make it possible, and both are visible in the change request before you approve it.

ConditionWhere it is checkedWhat you do
The older revision is permitted for that controller Firmware policy in the configuration repository Add it to allowed. The newest entry stays the default, so listing an older release does not make it the target for everything else.
The image permits the installed version to move backwards Declared inside the firmware image itself Nothing. It is read from the image and refused if the installed version is outside that range. 
# A controller allowed to move back one release, still defaulting to the newest
192.168.42.121:
  allowed: ["4.8.9", "4.9.1"]
  # default is 4.9.1, the newest allowed

# The instruction that performs the downgrade names the older revision explicitly
plc_ip: 192.168.42.121
action: firmware_update
target_version: "4.8.9"

Settings are preserved across a downgrade by the same backup and restore the controller performs during any firmware change. Settings introduced by a newer release have nowhere to go on the older one and are reported as restore errors in the controller's own log.

Vocabulary

The terms a pipeline uses, expressed in plant terms.

TermWhat it means here
Pull requestA change request. It shows the difference between what is running and what is proposed, and it holds your approval.
MergeAccepting the change request. This is the moment authorization exists; it is also what starts the job.
WorkflowThe stored procedure that carries out an approved change. It is fixed and reviewed like any other file in the repository.
RunnerThe service PC inside the plant network that executes the procedure. Without one, an approved change simply waits.
Dry runA rehearsal. Reads the controller, reports what it would change, writes nothing.
Audit logA tamper-evident record. Each entry carries a hash of the previous one, so a removed or edited line can be detected.

What holds, and what does not

Firmware and reboot are gated, not impossible

Denied for every device, with the denial recorded. One escape hatch exists: WAGO_ALLOW_METHODS re-enables a single named method in live mode. Treat putting a firmware method on that list as a decision with the same weight as the flash itself.

An uncommitted file authorizes nothing

The runner verifies that the instruction is committed and unmodified before acting on it. Editing a file on disk has no effect.

Every outcome is recorded

Approvals, refusals, successes, device-reported failures and interrupted runs all reach the audit log, and can be forwarded to a syslog collector outside the machine that writes them.

Four eyes is a repository setting

If the repository does not require an approving reviewer, the same person can propose and approve. That is permitted, and it is recorded as self-approved rather than disguised. Requiring a second person is a branch protection rule, not something this tooling can create.

A firmware change is not reversible by commit

A downgrade is a second firmware operation with its own risk and its own downtime. It is not an undo.

Devices are offline while they restart

A CC100 has taken ten minutes to return. Silence during a firmware change is expected and is not by itself a fault.

Values shown are read from the test rack: 18 controllers on firmware 04.09.01 build 31, comprising CC100, PFC200 G2, PFC300, Edge Controller, TP600 and WP400. Parameter identifiers and status codes are those returned by the devices themselves.

Drei Arten von Zugriff, und wer sie ausführen darf

Jeder Zugriff auf eine Steuerung gehört zu genau einer dieser Arten. Daraus ergibt sich, wer ihn ausführen darf. Der Server setzt das im Code durch; es ist keine Absprache, an die sich alle halten sollen.

Lesen

Assistent, direkt

Werte, Diagnose, Status. Das Gerät bleibt unverändert.

  • Firmware-Version und Build der gesamten Flotte
  • Status und Fortschritt während eines laufenden Updates
  • Jeder der rund 400 Parameter eines Geräts

Konfigurieren

Vorschlag mit Freigabe

Beschreibbare Parameter. Im GitOps-Betrieb schreibt der Assistent nicht auf das Gerät. Er legt stattdessen eine Änderungsdatei im Konfigurations-Repository an.

  • NTP-Server, SNMP, Hostname
  • Belegung der seriellen Schnittstelle
  • 0-0-docker-enabled

Eingriff

Nur namentlich

Neustart, Werksreset, Firmware. Im GitOps-Betrieb kann der Assistent so etwas nur vorschlagen. Im Live-Betrieb wird der Aufruf abgelehnt, solange die betreffende Methode nicht ausdrücklich freigeschaltet ist. Die Ablehnung steht in beiden Fällen im Log.

  • Neustart und Reboot
  • Firmware-Update und Downgrade
  • Werksreset, Formatieren

Wer beteiligt ist

Vier Beteiligte, vier klar getrennte Aufgaben. Keiner kann die Rolle eines anderen übernehmen.

Der Assistent

Liest die Flotte aus und entwirft Änderungsdateien. Die Verbindung zu den Steuerungen läuft über den MCP-Server und die WDA-REST-Schnittstelle.

Schreibt im GitOps-Betrieb nichts auf ein Gerät. Flasht keine Firmware, solange die Methode nicht ausdrücklich freigeschaltet ist.

Sie

Prüfen den Vorschlag, geben ihn frei, mergen ihn. Das ist die einzige Stelle im ganzen Ablauf, an der ein Mensch entscheidet.

Der Merge ist die Freigabe. Vorher passiert nichts am Gerät.

Das Konfigurations-Repository

Ein gewöhnliches Git-Repository: eine Datei pro Gerät, dazu die Firmware-Richtlinie. Darin steht, wie die Anlage aussehen soll.

Die Datei ist die Anweisung. Wer sie lokal ändert, ohne zu committen, hat nichts freigegeben.

Der Runner

Ein kleiner Dienst auf einem PC im Anlagennetz. Er beobachtet das Repository und führt an den Geräten aus, was freigegeben wurde.

Er muss im Anlagennetz stehen. Ein Rechner in der Cloud hat keine Route zu den Steuerungen.

Ablauf 1: einen Parameter ändern, Beispiel Docker

Gilt für jeden beschreibbaren Parameter. Docker steht hier stellvertretend, weil die Einstellung darüber entscheidet, was auf der Steuerung überhaupt läuft.

Container-Laufzeit auf 192.168.42.119 einschalten

0-0-docker-enabled  false → true
  1. Techniker

    Im Klartext sagen, was passieren soll

    "Docker auf der PFC300 unter 192.168.42.119 einschalten." Der Assistent liest zuerst den Istwert. Die Änderung setzt damit am tatsächlichen Zustand an, nicht an dem, den zuletzt jemand angenommen hat.

  2. Assistent

    Es entsteht eine Datei, kein Schreibzugriff

    Im GitOps-Betrieb wird der Schreibzugriff abgefangen. Zurück kommt eine Datei für das Gerät mit Parameter und Sollwert.

    # plcs/192.168.42.119.yaml
plc_ip: 192.168.42.119
managed_parameters:
  0-0-docker-enabled: true
  3. Techniker

    Pull Request öffnen und die Differenz lesen

    Der Pull Request stellt Ist und Soll gegenüber, wie ein Diff bei Quellcode. Bis hierher hat nichts die Steuerung erreicht.

  4. Runner

    Am Pull Request läuft automatisch ein Probelauf

    Der Runner liest die Istwerte aus der Steuerung und meldet, was er schreiben würde. Geschrieben wird nichts. Hier fällt auf, wenn ein Gerät nicht erreichbar ist oder jemand den Wert zwischenzeitlich von Hand verstellt hat.

    [192.168.42.119] Drift detected (1 parameter):
  0-0-docker-enabled: False → True
Dry-run. Pass --execute to apply.
  5. Techniker

    Freigeben und mergen

    Ihre Freigabe am Pull Request ist die Autorisierung. Sie hängt an Ihrem GitHub-Konto und wird nicht in die Datei getippt.

  6. Runner

    Geschrieben wird nur, was abweicht

    Derselbe Vergleich läuft noch einmal, diesmal schreibend. Parameter, die bereits stimmen, bleiben unberührt; ein zweiter Lauf richtet also keinen Schaden an. Im Auditlog steht, welche Parameter sich geändert haben. Wer freigegeben hat, steht am Pull Request.

Ablauf 2: eine Steuerung neu starten

Ein Neustart ist kein Parameter. Er passiert einmal, und kein späterer Commit nimmt ihn zurück. Deshalb steht er in einer Datei, die nach der Ausführung gelöscht wird.

Edge Controller 192.168.42.121 neu starten

ops/reboot-edge-121.yaml  0-0-device-reboot
  1. Assistent

    Der Aufruf wird verweigert, ein Vorschlag entsteht

    Der Server lehnt den Reboot ab und liefert eine Anweisungsdatei zurück. Das Feld approved_by bleibt leer.

    plc_ip: 192.168.42.121
action: invoke_method
method_id: 0-0-device-reboot
requires_human: CRITICAL
approved_by: ""
  2. Techniker

    Pull Request öffnen, er darf liegen bleiben

    Solange niemand freigibt, führt niemand etwas aus. Sie können den Vorschlag heute einstellen und erst im nächsten Wartungsfenster mergen.

  3. Techniker

    Im Wartungsfenster freigeben und mergen

    Der Merge löst den Neustart aus. Planen Sie ihn wie den Gang zum Schaltschrank, denn die Wirkung auf die Anlage ist dieselbe.

  4. Runner

    Einmal aufrufen, dann Datei löschen

    Nach erfolgreicher Ausführung verschwindet die Anweisung aus dem Repository und kann beim nächsten Lauf nicht versehentlich noch einmal greifen. Schlägt sie fehl, bleibt sie für den zweiten Versuch liegen.

Ablauf 3: Firmware-Update und Downgrade

Firmware ist die einzige Änderung, die sich nicht per Commit zurücknehmen lässt. Der Ablauf ist derselbe wie beim Neustart, mit zwei zusätzlichen Prüfungen.

Edge Controller 192.168.42.121 auf Build 31 bringen

ops/fw-edge-121.yaml  Ziel 4.9.1
  1. Techniker

    Prüfen, welche Version für dieses Gerät zugelassen ist

    Die Firmware-Richtlinie listet je Steuerung die zugelassenen Versionen. Nennen Sie keine, installiert der Runner die neueste davon.

    # firmware-policy.yaml
192.168.42.121: { allowed: ["4.9.1"] }
  2. Techniker

    Anweisung einstellen und freigeben

    Aufbau wie beim Neustart: ein Gerät, eine Version, ein leeres approved_by bis zum Merge.

  3. Runner

    Das passende Image kommt aus der Hardware, nicht aus dem Dateinamen

    Der Runner fragt die Steuerung nach Artikelnummer und Build, öffnet jedes verfügbare Image und vergleicht dessen Artikelliste damit. Passen zwei Images, bricht er ab und listet beide auf, statt zu raten.

    Device identity: order=0752-8303/8000-0002  firmware=04.09.01(31)
Resolved: TP-Linux_update_V040901_31 (build 31)
  4. Runner

    Zwei Prüfungen vor dem ersten Schreibzugriff

    Die Steuerung muss den Mindest-Build ihres Typs erreicht haben, und die installierte Version muss in dem Bereich liegen, den das Image selbst zulässt. Beides führt zum Abbruch, nicht zu einer Warnung.

  5. Runner

    Übertragen, installieren, neu starten

    Das Image geht in Blöcken auf das Gerät, die Steuerung installiert es und startet sich selbst neu. In dieser Zeit ist sie zeitweise nicht erreichbar. Der Fortschritt bleibt bei etwa 93 Prozent stehen und erreicht nie 100. Fertig ist der Vorgang, wenn der Status das sagt, nicht der Prozentwert.

    fwstatus: Started (3)  progress: 61%
[device unreachable - restarting]
fwstatus: Unconfirmed (4)  progress: 93%
Done. fwstatus: Inactive (0)  firmware version: 04.09.01

Downgrade auf eine ältere Version

Ein Downgrade ist derselbe Ablauf mit einer älteren Zielversion. Es braucht keinen Sondermodus und kein zweites Werkzeug. Zwei Bedingungen müssen erfüllt sein, und beide stehen im Pull Request, bevor Sie freigeben.

BedingungGeprüft wird sieIhr Anteil
Die ältere Version ist für diese Steuerung zugelassen in der Firmware-Richtlinie im Konfigurations-Repository Version in allowed eintragen. Die neueste bleibt Vorgabe, eine ältere aufzunehmen ändert daran nichts.
Das Image erlaubt den Rückschritt von der installierten Version im Firmware-Image selbst Nichts. Der Runner liest den Bereich aus dem Image und bricht ab, wenn die installierte Version außerhalb liegt. 
# Eine Steuerung darf eine Version zurück, Vorgabe bleibt die neueste
192.168.42.121:
  allowed: ["4.8.9", "4.9.1"]
  # Vorgabe ist 4.9.1

# Die Anweisung für das Downgrade nennt die ältere Version ausdrücklich
plc_ip: 192.168.42.121
action: firmware_update
target_version: "4.8.9"

Die Einstellungen übernimmt dieselbe Sicherung und Rücksicherung, die bei jedem Firmware-Wechsel läuft. Parameter, die es erst ab einer neueren Version gibt, finden auf der älteren kein Ziel. Sie tauchen im Geräteprotokoll als Restore-Fehler auf.

Begriffe

Was die Pipeline-Begriffe in der Anlage bedeuten.

BegriffBedeutung hier
Pull RequestDer Änderungsantrag. Er zeigt Ist gegen Soll und trägt Ihre Freigabe.
MergeDie Annahme des Antrags. Damit entsteht die Autorisierung, und damit startet die Ausführung.
WorkflowDer hinterlegte Ablauf, der eine freigegebene Änderung ausführt. Er liegt als Datei im Repository und wird geprüft wie jede andere.
RunnerDer PC im Anlagennetz, der diesen Ablauf ausführt. Fehlt er, bleibt eine freigegebene Änderung liegen.
Dry runDer Probelauf. Liest die Steuerung, meldet die geplante Änderung, schreibt nichts.
AuditlogDer manipulationssichere Nachweis. Jeder Eintrag trägt den Hash des vorherigen, ein gelöschter oder geänderter Eintrag fällt auf.

Was gilt, und was nicht

Firmware und Reboot sind gesperrt, nicht unmöglich

Abgelehnt für jedes Gerät, die Ablehnung steht im Auditlog. Eine Ausnahme gibt es: WAGO_ALLOW_METHODS schaltet im Live-Betrieb genau eine benannte Methode wieder frei. Eine Firmware-Methode dort einzutragen wiegt so schwer wie der Flashvorgang selbst.

Ohne Commit keine Freigabe

Der Runner prüft vor jeder Aktion, ob die Anweisung committet und unverändert ist. Eine Änderung auf der Festplatte bleibt folgenlos.

Jedes Ergebnis steht im Log

Freigaben, Ablehnungen, Erfolge, Gerätefehler und abgebrochene Läufe. Auf Wunsch geht alles zusätzlich an einen Syslog-Server außerhalb des Rechners, der das Log schreibt.

Vier Augen sind eine Repository-Einstellung

Verlangt das Repository keinen zweiten Prüfer, darf dieselbe Person vorschlagen und freigeben. Das ist erlaubt und wird als Selbstfreigabe ausgewiesen. Einen zweiten Prüfer erzwingt eine Branch-Protection-Regel, nicht dieses Werkzeug.

Firmware lässt sich nicht per Commit zurücknehmen

Ein Downgrade ist ein zweiter Firmware-Vorgang mit eigenem Risiko und eigenem Stillstand. Es ist kein Undo.

Während des Neustarts ist das Gerät weg

Eine CC100 hat zehn Minuten gebraucht, bis sie wieder antwortete. Funkstille während eines Firmware-Wechsels ist normal und für sich genommen kein Fehler.

Alle Werte stammen vom Prüfstand: 18 Steuerungen auf Firmware 04.09.01 Build 31, darunter CC100, PFC200 G2, PFC300, Edge Controller, TP600 und WP400. Parameternamen und Statuscodes sind die, die die Geräte selbst liefern.
